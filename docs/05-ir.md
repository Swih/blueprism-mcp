# IR : ce que l'agent remplit, ce que le générateur transforme

L'IR (représentation intermédiaire) est le **seul** format que le LLM produit. Il est validé par zod, puis transformé de façon déterministe en XML Blue Prism 7.5.1. Il décrit **l'intention** (quels éléments, quelles actions) ; le générateur se charge de **la plomberie** (GUID, liens, pages standard, arguments du catalogue, mise en page).

## Objet (`ObjectSpec`)

```ts
type ObjectSpec = {
  name: string;                 // "RPA Challenge - Form" (convention <Application> - <Écran>)
  description: string;          // narrative de l'objet
  runMode: "Foreground" | "Background" | "Exclusive";
  application: ApplicationSpec;
  elements: ElementSpec[];
  actions: ActionSpec[];        // une action = une page, publique ou privée
};

type ApplicationSpec =
  | { kind: "BrowserLaunch"; name: string; browserPath: string; url: string; extraArgs?: string[] }
  | { kind: "BrowserAttach"; name: string; /* paramètres selon le catalogue apptypes */ };

type ElementSpec = {
  key: string;                  // identifiant stable dans l'IR (sert aux GUID et aux références)
  name: string;                 // "Form - First Name Field"
  type: string;                 // type AMI : WebTextEdit, WebButton, WebElement…
  match: Record<string, string | number | boolean>;    // identifiants en correspondance (inuse)
  dynamic?: string[];           // attributs alimentés par chaque étape, ex. ["wXPath"]
  captured?: Record<string, string | number | boolean>; // valeurs observées, non utilisées
  rationale?: string;           // pourquoi ces attributs (repris dans le rapport)
};

type ActionSpec = {
  name: string;                 // "Set Field First Name", "Click Button - Start"
  description: string;          // narrative de la page
  published?: boolean;         // false pour Attach et les helpers internes
  inputs: ParamSpec[];
  outputs: ParamSpec[];
  steps: StepSpec[];
};

type ParamSpec = { name: string; type: "text" | "number" | "flag" | "date" | "datetime" | "password"; description: string; defaultValue?: string | number | boolean };

type ElementParams = { name?: string; params?: Record<string, string>; args?: Record<string, string> };

type StepSpec =
  | { kind: "launch" }                                              // Navigate Launch sur l'application
  | { kind: "close" }                                               // Navigate WebCloseApplication
  | { kind: "ensureAttached"; args?: Record<string, string> }        // connexion -> décision -> Attach si nécessaire
  | { kind: "callPage"; page: string; inputs?: Record<string, string>; outputs?: Record<string, string> }
  | ({ kind: "waitFor"; element: string; condition?: string;        // défaut : WebCheckExists
      timeoutSeconds: number | string; expected?: string; onTimeout: ExceptionSpec } & ElementParams)
  | ({ kind: "write"; element: string; value: string } & ElementParams) // value : expression BP
  | ({ kind: "read"; element: string; action: string; into: string } & ElementParams)
  | ({ kind: "act"; element: string; action: string } & ElementParams) // WebClick, WebSendKeys…
  | { kind: "calc"; expression: string; into: string }
  | { kind: "raise"; exception: ExceptionSpec };

type ExceptionSpec = { type: "System Exception" | "Business Exception" | string; detail: string };
```

`into` désigne un data item de la page. Le générateur crée les data items nécessaires : entrées, sorties et cibles de `read` / `calc`.

`params` alimente les attributs Dynamic de l'élément ; `args` alimente les arguments de l'action ou condition AMI. Le générateur refuse un paramètre dynamique manquant ou attribué à un élément statique. Un attribut ne peut pas appartenir à la fois à `match` et `dynamic`.

`name` permet de donner un nom court et lisible aux stages Wait, Write, Read et Navigate, par exemple `Wait Field` ou `Write Value`. L'expression et les détails restent dans les propriétés du stage.

`ensureAttached` sélectionne la lecture de connexion dans le catalogue du mode applicatif : `WebIsConnected` pour BrowserLaunch, `IsConnected` pour BrowserAttach sur l'installation 7.5.1 vérifiée. Un ancien catalogue sans racine BrowserAttach doit être réextrait ; il n'est pas remplacé silencieusement par celui de BrowserLaunch.

`expected` est une expression BP, par exemple `True`, `False`, `[Expected Text]` ou `"Ready"` avec les guillemets de chaîne. Il vaut `True` par défaut pour une condition flag ; une condition texte requiert une valeur explicite. Un timeout variable doit être une référence numérique déclarée comme `[Wait Timeout]`, pas une expression arithmétique libre. Sa valeur positive à l'exécution reste de la responsabilité de l'appelant.

`callPage.inputs` contient des expressions ; `callPage.outputs` associe les noms de sorties aux data items de l'appelant. Les paramètres dotés d'un `defaultValue` peuvent être omis à l'appel généré. Les références de pages, noms d'entrées/sorties, data items et cycles d'appel sont vérifiés. Les helpers privés restent appelables à l'intérieur de l'objet, mais sont refusés dans le banc de test externe.

## Ce que le générateur garantit (règles de [01-spikes.md](01-spikes.md))

| # | Garantie |
|---|---|
| G1 | Racine `appdef` typée `Application` (type, basetype, datatype `unknown`, diagnose). |
| G2 | `apptypeinfo` complet selon le catalogue `apptypes` (5 paramètres pour BrowserLaunch en 7.5.1, dont `prelaunchbrowser`). |
| G3 | Chaque élément porte **tous** les identifiants du catalogue dans leur ordre ; `inuse` pour `match` et `dynamic`. |
| G4 | Chaque étape applicative porte **tous** les arguments déclarés pour son action ou sa condition. |
| G5 | L'action et la condition sont **autorisées** pour le type d'élément (catalogue), sinon erreur de génération explicite. |
| G6 | GUID = uuid v5 d'un chemin stable `objet/page/typeÉtape/nomÉtape`, avec une **vérification d'unicité** qui échoue plutôt que d'écrire un doublon. |
| G7 | Page principale avec `ProcessInfo` (options de code pour un objet), pages `Initialise` et `Clean Up` présentes. |
| G8 | Paramètres des étapes `Action` avec `friendlyname`. |
| G9 | Pas de `loginhibit` par défaut. |
| G10 | `waitFor` : branche timeout, puis `WaitEnd`, puis étape `Exception` avec le type et le détail fournis. |
| G11 | Mise en page lisible : colonne principale, branches d'erreur à droite, data items regroupés. |

## Banc de test (`TestHarnessSpec`)

```ts
type TestHarnessSpec = {
  name?: string;                        // défaut : <object> - Test
  object: string;                       // objet par défaut des appels
  calls: { object?: string; action: string; inputs?: Record<string, string>; expect?: Record<string, string> }[];
  cleanupAction: string;                // ex. "Terminate" : appelé en Recover avant de relancer l'exception
  cleanupObject?: string;               // défaut : object
};
```

Le générateur accepte un objet ou une liste d'objets et vérifie chaque appel contre la signature de l'objet concerné. Le process appelle les actions dans l'ordre, expose les sorties attendues comme sorties du process, et contient le chemin `Recover → cleanupAction → rethrow`, avec conservation de l'exception courante. Il ne place pas de Resume avant ce rethrow : réactiver la récupération normale à cet endroit pourrait renvoyer l'exception vers le même Recover.

La vérification des sorties (relecture indépendante via le listener `outputs`) reste externe au process. Les essais natifs actuels utilisent les scripts de validation Python/PowerShell ; leur intégration dans l'API publique de `@bpdev/bridge` reste à terminer. Si le nettoyage échoue lui-même, cette nouvelle erreur peut remplacer l'erreur initiale ; cette version n'isole pas encore cet échec secondaire.

## Hors périmètre de cette version

Mode UIA et fenêtres natives, injection dans le template de process, exploration automatique complète du site et contrôle d'unicité au runtime BP. Les contrôles XPath du [relevé RPA Challenge](06-dynamic-spy.md) ont été effectués dans le navigateur ; le générateur seul n'inspecte pas le DOM.
